CLI reference

Conficius manages configured dotfile links and inspects installed package tools. Package updates and dotfile linking are previews unless you pass --apply. Preview commands can still run package-manager queries and contact network services; a dry run is not an offline mode.

conficius [global options] command [command options]
conficius --help
conficius packages update --help
conficius help packages

Install and start

Download a CLI or TUI archive from GitHub releases. Choose darwin for macOS or linux, then arm64 or amd64. Verify against the release’s checksums.txt, extract, and put the binary on your PATH.

CLI archives use conficius_VERSION_OS_ARCH.tar.gz; TUI archives use conficius-tui_VERSION_OS_ARCH.tar.gz. Either binary runs independently.

conficius init
conficius dotfiles link
conficius packages pms
conficius packages outdated

Edit the commented examples in conficius.toml before linking. To build from source, use Go 1.26.8 or newer:

git clone https://github.com/jccguimaraes/conficius.git
cd conficius
go build -o ./bin/conficius ./cmd/cli
go build -o ./bin/conficius-tui ./cmd/tui

Global options

--config FILE
Use an explicit file for the command’s config domain: dotfiles for init, dotfiles, and config migrate; packages for profile-aware package commands and config resolve. packages pms does not load config. Put this before the command; supply it only once. config layout rejects this flag.
--help, -h
Show help. Available on subcommands too.
--version, -v
Print the CLI version.

Command index

  • init; config resolve; config layout; config migrate
  • dotfiles audit; dotfiles link [tools...]
  • packages pms; packages doctor; packages outdated
  • packages vulnerabilities; packages update
  • packages go-tools import MODULE VERSION COMMAND [COMMAND...]
  • wisdom prints a random Conficius proverb: a parody, not a Confucius quote. No command-specific options.
  • help (alias h) lists commands or shows help for a command.

The config, dotfiles, packages, and packages go-tools groups organize the subcommands below; use their help to browse available operations.

Configuration

Dotfiles and packages have independent TOML files. Dotfiles discovery checks --config FILE first, then conficius.toml in the working directory and each parent, then $XDG_CONFIG_HOME/conficius/conficius.toml (normally ~/.config/conficius/conficius.toml). Relative link sources use that file’s directory.

Package discovery uses $XDG_CONFIG_HOME/conficius/config.toml, defaulting to ~/.config/conficius/config.toml, or the native macOS path ~/Library/Application Support/conficius/config.toml. If both exist, discovery fails rather than choosing one. Linux uses the same location for both layouts. An explicit package --config FILE bypasses discovery. Package commands never discover repository conficius.toml; missing central config uses defaults, while invalid config fails.

init

Create a commented version-2 conficius.toml in the working directory, or at --config FILE. This writes immediately; it has no --apply option and refuses to overwrite an existing file.

conficius init
conficius --config ~/dotfiles/conficius.toml init
conficius --config ~/.config/conficius/config.toml config resolve --profile work --verbose

config resolve

--profile NAME
Select a package profile. Selection order: command flag, CONFICIUS_PROFILE, top-level profile in the configuration, then default. Package config requires version 2.
--json
Print the resolved profile as JSON, rather than the package-output envelope.
--verbose
Include provenance showing where resolved settings came from.

config layout

Preview creation or relocation of the central package config. Choose --xdg or --os-native, never both. Without either flag, use the stored layout, defaulting to xdg. --apply writes the change and retains the old config beside its original path as .conficius-layout-backup-*. This command rejects --config; it does not relocate dotfiles. Conflicting central package configs must be resolved first.

conficius config layout --xdg
conficius config layout --xdg --apply
conficius config layout --os-native
conficius config layout --os-native --apply

config migrate

Print a dotfiles version-2 migration preview by default. --apply creates a backup and replaces the configuration atomically.

conficius config migrate
conficius config migrate --apply

Minimal link configuration

Create the source files or directories before linking. Tool names are free-form; one tool can have several links.

version = 2

[tools.zsh]
links = [
  { source = "dotfiles/zsh/.zshrc", target = "$HOME/.zshrc", platforms = ["linux", "darwin"] },
]

[tools.nvim]
links = [
  { source = "dotfiles/nvim", target = "$XDG_CONFIG_HOME/nvim" },
]

Targets expand $VAR and ${VAR}; standard HOME and XDG variables have defaults. Omit platforms, or use an empty list, to enable a link on every platform. Values such as linux, darwin, and windows use Go OS names.

Directory links are live directories, not copies. If an application writes caches, sessions, sockets, credentials, or other runtime files inside a linked directory, it writes into your repository. Add suitable repository .gitignore rules before use, or link only the configuration files and keep runtime state outside the repository. Gitignore does not prevent writes, protect secrets, or remove files already tracked by Git.

Manage Conficius from your dotfiles repository

This macOS example keeps Conficius's own package config in ~/dotfiles and links its directory into ~/.config. macOS uses the Go platform name darwin; the package config still uses the supported xdg layout, not os-native.

~/dotfiles/
├── conficius.toml
└── .config/
    └── conficius/
        └── config.toml

Create the source directory and files first. Replace /path/project-x and /path/project-y with your existing project directories, or create those directories before using their scopes. They are placeholders, not paths to create at the filesystem root. No root privileges or sudo are needed for these user-owned config files and links.

Save this complete link config as ~/dotfiles/conficius.toml:

version = 2

[[tools.conficius.links]]
source = ".config/conficius"
target = "$HOME/.config/conficius"
platforms = ["darwin"]

Save this complete package config as ~/dotfiles/.config/conficius/config.toml:

version = 2
layout = "xdg"
profile = "default"

[[profiles.default.projects]]
name = "project-x"
path = "/path/project-x"

[[profiles.work.projects]]
name = "project-y"
path = "/path/project-y"

If ~/.config/conficius already exists as a regular directory, linking will not overwrite or merge it, even with --force. Back it up, copy any settings you need into the repository source, then manually relocate the existing directory outside the target path before applying. Preserve the backup until you verify the new setup. Other conflicting real files or unrelated symlinks also require manual resolution.

Preview first, inspect the target, then apply:

conficius --config ~/dotfiles/conficius.toml dotfiles link conficius
conficius --config ~/dotfiles/conficius.toml dotfiles link conficius --apply

Add "linux" to platforms to use this link on Linux too; omit platforms to allow every platform. The target above is fixed at ~/.config/conficius and ignores a custom XDG_CONFIG_HOME. For that setup, use target = "${XDG_CONFIG_HOME}/conficius" instead; the resolved target must remain inside your home directory.

After linking, edit ~/dotfiles/.config/conficius/config.toml; reads through the central path see the same file. In TUI package views, r reloads settings and project scopes. Press p, then Enter, to switch profiles for the session without changing the file. The selected profile supplies its projects alongside default/global package scopes: default adds project-x, while work adds project-y. Profiles are independent; work does not inherit default projects or manager settings.

Version control the repository files deliberately: project paths are machine-local and may need adjustment on another machine. Do not commit secrets. Directory links are live, so runtime writes also land in the repository; .gitignore does not protect secrets or remove already tracked files.

Repository linking and config layout migration are separate workflows. Choose repository linking for this self-managed setup; changing layout does not move files automatically. Layout relocation requires a regular source config file and refuses a symlink source. A directory symlink does not itself make the contained config.toml a symlink; do not treat migration as a way to manage or relocate repository links.

Package config fields

version
Required: 2. Package config schema version.
layout
Optional: "xdg". "xdg" or "os-native"; chooses the default for an explicit config layout action, not automatic relocation.
profile
Optional: "default" fallback. Selection priority: --profile NAME, CONFICIUS_PROFILE, this field, then default.
profiles.<name>.managers.<manager>.enabled
Optional: true. Managers stay enabled unless explicitly disabled. Enabling one does not disable others.
profiles.<name>.projects[].name
Required per project. Unique project name within the profile, used by --profile-project.
profiles.<name>.projects[].path
Required per project. Absolute path or path relative to the package config file's directory, not the repository root. Supports $HOME, ${HOME}, and other set environment variables via $VAR or ${VAR}; HOME/XDG variables have defaults. Unset variables without defaults fail; ~ is not expanded.
profiles.<name>.projects[].allow_manifest_changes
Optional: false. Set true explicitly to permit native project updates that may change manifests or lockfiles. Git overrides do not bypass this guard.
vulnerabilities.mappings / vulnerabilities.euvd
Optional. Explicit vulnerability identities; see vulnerability checks and security caveats.

For example, disable a manager with [profiles.work.managers.brew] and enabled = false. Native manifests and lockfiles remain the authority for versions and dependency declarations; Conficius does not store a second version policy or executable overrides.

conficius config resolve --profile work --verbose
conficius packages outdated --profile work --profile-project project-y --pm npm

The example leaves project mutation disabled. Set allow_manifest_changes = true in the matching project entry only when you intend to permit updates, then preview before using --apply.

TUI configuration and profiles

conficius-tui --config ~/dotfiles/conficius.toml
conficius-tui --package-config ~/.config/conficius/config.toml
conficius-tui --config ~/dotfiles/conficius.toml --package-config ~/.config/conficius/config.toml

The TUI’s --config selects dotfiles only; --package-config selects packages. From Home, scopes, or outdated packages, press p for the profile picker and Enter to select. Selection is a session override, not a disk write. Press r in package views to reload package settings and project scopes before refreshing. Package lists use compact rows; Enter opens details. Missing dotfiles show optional onboarding: “Add your dotfiles when you’re ready.” Run conficius init in your dotfiles repo when needed; package use does not require dotfiles.

In outdated packages, Space marks a row, a toggles all, u previews marked upgrades, and U previews all. In the preview, y applies and n or Esc cancels. v opens vulnerabilities; o returns to outdated packages. Confirmed upgrades run in the terminal, then restart the TUI. TUI execution does not use the CLI’s fresh-query, accepted-hash, durable-log, or outcome-verification workflow.

Dotfiles

dotfiles audit

Audit environment layout, Zsh configuration when the detected shell is Zsh, and configured link state. This does not repair files.

--xdg or --os-native
Exactly one layout choice is required. Use XDG directories or OS-native configuration directories. Environment alternatives: CONFICIUS_XDG and CONFICIUS_OS_NATIVE; do not enable both.
--strict
Return nonzero when the audit contains warnings or errors.
--json
Write an audit report with schema_version: 1.
conficius dotfiles audit --xdg
conficius dotfiles audit --os-native --strict --json

dotfiles link [tools...]

Preview links for all configured tools by default. Positional tool names select a subset; platform filters still apply.

--exclude TOOL
Exclude a configured tool. Repeat for multiple exclusions.
--apply
Create missing parent directories and symlinks after validation.
--force
Allow replacement of a conflicting symlink only when its destination resolves inside this configuration repository. Does not authorize replacing real files, real directories, or unrelated external symlinks.
--json
Write link results in a schema_version: 1 envelope with data.
conficius dotfiles link
conficius dotfiles link zsh nvim --exclude nvim
conficius dotfiles link zsh --apply

Sources must exist and resolve inside the configuration directory. Targets must remain inside the home directory, including existing parent symlinks. Duplicate targets and unsafe paths are rejected. Existing correct links are left alone; move conflicting real files yourself after backing them up. Link application revalidates state and attempts rollback on failure; inspect any reported rollback error before retrying.

Package inspection

Shared package options

These options apply to packages doctor, packages outdated, packages vulnerabilities, and packages update, not to every command in the group.

--pm NAME
Limit managers; repeat to select more than one, for example --pm mise --pm npm. Supported names appear in the matrix. Without this flag, manager discovery is not restricted by a CLI filter; resolved profile settings still affect queries and selection.
--global
Select global installations only. Cannot be combined with --project. Use scope selectors separately rather than mixing global, path, and named-project selection.
--project PATH
Select a project path; repeat for multiple roots. Relative CLI paths are based on the working directory.
--profile NAME
Select a configured profile; also reads CONFICIUS_PROFILE.
--profile-project NAME
Select a named project in the resolved profile; repeat for multiple projects. Named-project selection takes precedence over explicit project paths.
--json
Write JSON with schema_version: 1, snapshot (timestamp, platform, architecture, CLI version), and command-specific data.

Without scope selectors, queries include global packages plus all configured profile projects. If no projects are configured, the working directory is included when it contains one of five project files: package.json, Cargo.toml, go.mod, mise.toml, or .mise.toml; otherwise only global packages are inspected. Recognized npm workspaces are expanded. A missing discovered config is allowed for package inspection; invalid configuration is not ignored.

Go project discovery uses go.mod independently of mise: a root containing both go.mod and mise configuration can inspect module dependencies and the Go runtime through separate managers.

packages pms

List all 13 supported managers and availability. Its only command-specific flag is --json. Reports can include resolved executable, manager version, tested-version status, and capabilities; support does not mean a manager is installed.

packages doctor

Check manager environment integrity and selected project roots without freshness queries. Accepts the shared package options. Use this to investigate executable paths, prefixes, and project setup before updating.

packages outdated

Query available updates from native managers. Accepts the shared package options plus:

--offline
Read installed inventory without network freshness checks. Reports freshness as unknown, not up-to-date. Offline output can include command collision candidates and PATH resolution. It does not establish update availability.
--check
For online queries: exit 0 when no updates are found, 1 when updates exist, and 2 on query failure. Without this flag, finding updates is not itself an error.
conficius packages pms --json
conficius packages doctor --pm npm --global
conficius packages outdated --project ./app --pm npm
conficius packages outdated --global --check
conficius packages outdated --offline --json

Offline --check cannot detect updates: successful inventory exits normally. The offline text branch maps query failures to exit 2 with --check; the offline JSON branch returns the query error directly. Do not treat either offline success as a freshness assertion.

apt inspects global system packages on Debian, Ubuntu, and other apt-based Linux systems only. Inventory uses dpkg-query; outdated checks use apt-get --simulate against locally cached package lists, not live latest versions. Inspection never refreshes apt lists or escalates privileges. To refresh lists, explicitly run sudo apt-get update yourself as a separate step before inspection, or on Linux, press c (Update package cache, currently APT) on TUI package scopes/results. The TUI previews the command: y approves; n/Esc cancels. It runs sudo -- <apt-get> update --error-on=any without a shell through the controlling TTY; sudo handles passwords, while root runs apt-get directly. Success restarts the TUI and refreshes outdated/security results; failure or cancellation shows a notice and leaves local inventory only. Offline mode reads inventory only, with freshness unknown. Project operations and automated package updates are unsupported. Debian security identity mapping is not implemented; coverage remains unknown, not clean.

Go project inventory runs go list -m -json -mod=readonly all with GOPROXY=off, GONOPROXY=none, GOSUMDB=off, and GOTOOLCHAIN=local. It uses cached module metadata only; cache misses are query errors, not empty or healthy inventory. Project outdated checks run go list -m -json -mod=readonly -u all; they may access the network and populate metadata caches but do not write go.mod. By default, outdated candidates include only direct dependencies and modules providing explicitly declared tool packages in the scope's go.mod, including indirect tool modules. Vulnerability scans still use the full module graph, including indirect dependencies. Replaced modules are excluded from outdated candidates; Go project updates are unsupported.

Online Homebrew queries run brew update before brew outdated. This refreshes local Homebrew metadata even during update previews or vulnerability checks that query outdated packages. Offline inventory skips freshness queries.

Vulnerability checks

packages vulnerabilities

Check exact installed versions using OSV and EUVD evidence. Accepts the shared package options plus --transitive, which requests transitive inventory where the adapter supports it. The command also queries available updates to annotate findings. It has no offline mode and does not install fixes.

conficius packages vulnerabilities --global --pm npm
conficius packages vulnerabilities --project ./app --transitive --json
  • OSV requires reliable ecosystem identity. Built-in inventory metadata supplies identities where available; npm has a direct mapping. Other packages may require explicit [[vulnerabilities.mappings]] entries. Never map an OS runtime or distribution package to an unrelated same-named registry package merely to obtain results.
  • Go project modules: native OSV identities use ecosystem Go and the actual module path/version, including versioned replacement modules. Local replacements have no published identity and are omitted from native inventory; this is a coverage gap, not a clean security result.
  • Go relevance: package loads classify modules as application, test, tool, or graph-only (in that precedence). Application includes imported indirect modules. Tool findings have separate counts. Graph-only modules remain scanned but are hidden by default: use --include-graph-only or TUI g; JSON always retains full evidence with dependency_class and scan_scope. Counts describe evidence, not unique CVEs. Loads use the selected Go environment’s OS, architecture, CGO and GOFLAGS/build tags, not every platform or tag combination. These are module/version matches, not vulnerable-call reachability. Offline package-loading failures retain graph evidence and report incomplete inspection, never a clean result; graph-only then means usage unconfirmed.
  • EUVD requires product and vendor identity. Built-in identities or [[vulnerabilities.euvd]] mappings identify the product. Results are checked against vendor, product, and installed version; unsupported version rules produce unknown evidence, not a clean result.
  • Unmapped, unknown, and error results are coverage gaps. An empty advisory list is not proof that a package is safe. Inventory-only adapters can still contribute scan data without supporting outdated queries or updates.
  • Global scans also inspect available package-manager binaries. Manager enablement and selected scopes control inventory; there is no separate profile security-selection policy.
  • OSV and EUVD evidence stays separate; the same CVE can appear from both sources. Summary counts describe evidence, not necessarily unique vulnerabilities.
  • An available upgrade is not necessarily a security fix. Review advisory ranges and upgrade notes; the latest available version can still be affected.
  • Findings alone do not provide a dedicated CI failure threshold. Inventory, freshness, or scan errors can return nonzero even when JSON evidence was emitted; inspect both the exit status and report.
# Add only after verifying identity against the advisory source.
[[vulnerabilities.mappings]]
manager = "mise"
package = "example"
ecosystem = "Go"
name = "example.org/module"

[[vulnerabilities.euvd]]
manager = "mise"
package = "node"
product = "Node"
vendor = "nodejs"

CONFICIUS_OSV_URL and CONFICIUS_EUVD_URL override service endpoints. These services receive package identity and version-related queries. Use trusted endpoints; endpoint overrides are not CLI flags.

Updates and safeguards

packages update

Preview manager-specific update plans by default for enabled managers and selected scopes. Plans show commands, scope, state hashes, and mutation impact. Accepts the shared package options plus:

--include PACKAGE
Include a package by manager:name or a globally unique name. Repeat for multiple selections.
--exclude PACKAGE
Exclude a package using the same selector syntax. Repeat as needed.
--apply
Execute update commands interactively. Requires explicit scope intent through --global, --project PATH, --profile NAME, or --profile-project NAME.
--yes
Use accepted plan hashes for non-interactive CLI execution. Requires --apply. This is not blanket approval for changed plans and does not guarantee that underlying tools never prompt.
--accept-plan HASH
Accept an exact state hash; repeat for every selected plan. Requires --yes. Missing, extra, stale, or no-longer-selected hashes are rejected.
--best-effort
Continue to later plans after a plan fails. Requires --apply. Default behavior stops after failure; continuing does not make failures successful.
--allow-dirty
Permit project mutation when the containing Git repository has uncommitted changes.
--allow-unversioned
Permit project mutation outside a Git repository.
--allow-untested-manager
Allow application with manager versions outside declared tested ranges. Does not add missing adapter capabilities.
# Preview first; no package updates are executed.
conficius packages update --global --pm npm --include npm:typescript
conficius packages update --global --pm npm --include npm:typescript --json

# Apply the reviewed selection interactively.
conficius packages update --global --pm npm --include npm:typescript --apply

# For automation, replace HASH_FROM_PREVIEW with each reviewed plan hash.
conficius packages update --global --pm npm --include npm:typescript \
  --apply --yes --accept-plan HASH_FROM_PREVIEW
  1. Inspect manager status and preview the exact intended scope. --json works for previews but is rejected with --apply.
  2. For project mutation, explicitly allow manifest changes in the matching profile project. By default its containing Git repository must be clean. CLI flags --allow-dirty and --allow-unversioned bypass only their respective Git checks. The TUI instead asks Continue with uncommitted changes, lists affected project paths, and warns that there is no automatic rollback. Press y to approve dirty Git state for this batch, then review and confirm the normal command preview; n or Esc cancels. Cancellation, a new preview, refresh, profile changes, and restart clear approval. Execution rechecks Git safety, so newly dirty projects require confirmation. TUI unversioned projects remain blocked; neither interface bypasses allow_manifest_changes = true.
  3. Application checks manager version ranges, then re-queries available updates and rebuilds plans. Fresh-query failures abort execution. Automation must accept the refreshed plans exactly; if state changed, preview and review again.
  4. A durable update log is written before execution. Failure to create it prevents updates. Commands run through the native managers; permission prompts and service impacts depend on the manager.
  5. Execution outcomes are verified against installed state and the log is finalized. Partial changes can remain after failure; review outcomes and any recovery guidance before retrying.

Current CLI limits. Manager-version and project-mutation checks run against the initial plans, before the fresh query; the refreshed plans are not checked again by those guards. Interactive execution does not require accepted hashes or another confirmation for refreshed plans. An initial query error can still allow successfully queried plans to run and then be returned after execution. Preview output is not a frozen execution contract.

No universal rollback. Native package updates can alter manifests, lockfiles, installed binaries, and services. Keep recoverable configuration and project backups. A dry run avoids executing update commands, but it can still query registries and run manager inspection commands.

Logs and Go tool records

State lives in $XDG_STATE_HOME/conficius, falling back to ~/.local/state/conficius.

Update logs

Applied updates write timestamp-named JSON files under updates/. Logs contain start/completion times, status, plans, outcomes, and error text. Status starts as planned and is finalized as completed, failed, or interrupted. Abrupt termination can leave an unfinished planned log.

The newest 30 JSON logs are retained. New log directories use mode 0700; log files use 0600. Home-directory prefixes in plan directories and package paths become ${HOME}. Error redaction replaces home paths and common token=, password=, passwd=, secret=, and API-key assignments. Redaction is limited; review logs before sharing. Logs are not a full transcript or automatic restore point.

packages go-tools import MODULE VERSION COMMAND [COMMAND...]

Immediately append an ownership record to go-tools.json in the state directory. Supply a module, version, and at least one command. No command-specific flags; no --apply needed. This records ownership only: it neither installs tools nor changes installed binaries.

conficius packages go-tools import golang.org/x/tools v0.30.0 stringer

Global Go inventory and command ownership use the journal only; the adapter does not scan installed binaries or infer ownership from build metadata. An import record is not proof that the recorded binary/version is installed. Verify module, version, and command ownership before recording them.
